# 产品说明｜从“统计账单”到“理解真实消费”

## 1. 项目背景

微信、支付宝和银行卡均能展示交易流水，但各平台字段、分类与统计范围并不一致。用户想做月度复盘时，仍需手动合并账单、判断重复项、修正分类，并处理朋友还款与群收款。

项目围绕一个具体问题展开：

> 如何降低个人月度复盘的操作成本，并让统计结果更接近用户真正承担的消费？

## 2. 需求拆解

### 整理

- 识别账单来源
- 统一时间、金额、商户、交易方向等字段
- 合并多份文件
- 识别跨平台重复流水

### 理解

- 依据商户、说明与原分类识别消费场景
- 区分消费、收入、退款与转账
- 保留原始信息与调整结果
- 对不确定记录给出提示

### 复盘

- 展示流水总支出与个人实际承担金额
- 对比不同月份和消费类别
- 标记高额支出
- 输出可追溯的复盘提示

## 3. 核心问题：流水金额 ≠ 个人实际承担

以聚餐垫付为例：

| 记录 | 流水 |
|---|---:|
| 用户先支付聚餐费用 | -¥300 |
| 朋友返还 AA 金额 | +¥200 |
| 流水显示总支出 | ¥300 |
| 用户实际承担 | ¥100 |

直接统计支出会高估个人消费。产品因此增加“疑似关联返还”和“个人实际承担”两个口径。

## 4. 关联判断

作品集原型采用可解释的轻量规则：

1. 收入备注出现“AA、返还、还款、聚餐”等语义
2. 收入与某笔消费处于相近日期
3. 收入金额不超过候选消费金额
4. 优先匹配描述语义相近、时间距离更短的消费
5. 输出疑似关系与计算结果，保留人工复核

该方案用于展示数据产品思路，不承担财务记账或审计功能。

## 5. 重复流水识别

银行卡流水可能再次记录微信或支付宝交易。原型根据以下信息标记疑似重复：

- 金额一致
- 时间接近
- 来源不同
- 银行流水描述中出现支付平台或商户线索

重复项默认不进入核心统计，同时在明细中保留。

## 6. 分类规则

系统读取“交易对象 + 商品说明 + 平台原分类”，再映射至统一分类。当前分类包括：

- 正餐
- 饮品零食
- 交通
- 购物
- 住房生活
- 文化娱乐
- 学习成长
- 医疗健康
- 会员订阅
- 人情往来
- 其他

无法判断的交易归入“其他”，避免为了提高分类覆盖率而强行推断。

## 7. AI 协作边界

### AI 参与

- 页面代码生成与调试
- 数据规则的初步实现
- 交互与文案迭代

### 人负责

- 识别真实需求
- 定义计算口径
- 判断误分类与异常结果
- 将生活语义转化为规则
- 用真实场景验证结果
- 决定取舍与后续迭代

## 8. 验证方法

每轮功能完成后，按以下顺序复核：

1. 导入结果是否完整
2. 收支方向是否正确
3. 分类是否符合消费意图
4. 重复项是否被误删
5. 朋友返还是否关联到正确消费
6. 汇总金额能否由明细追溯
7. 不确定结果是否明确提示

## 9. 局限与后续方向

- 不同平台导出格式持续变化，需要维护字段映射
- 仅凭规则无法准确理解所有转账关系
- 复杂的多人分摊需要交互式人工确认
- 当前版本正式支持 CSV / TXT
- Excel、PDF、长期预算与跨设备同步属于后续扩展方向
